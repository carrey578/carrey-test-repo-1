## 二、候选方案对比

### 方案 A：增强服务器检查脚本

| 项目 | 内容 |
|------|------|
| **涉及文件** | `scripts/check-dev-env-server.sh` |
| **改动内容** | 新增：内存检查、磁盘检查、Node 版本检查、Git 状态检查 |
| **为什么值得做** | 当前脚本检查项较少，增强后可覆盖更多开发环境要素 |
| **风险点** | 低（只读检查，不会破坏系统） |
| **预期收益** | 提升服务器巡检覆盖率 |

### 方案 B：增强本地检查脚本

| 项目 | 内容 |
|------|------|
| **涉及文件** | `tools/check-dev-env-local.ps1` |
| **改动内容** | 新增：Node 版本检查、npm 检查、OpenClaw 本地检查（若存在） |
| **为什么值得做** | 与服务器脚本对齐，增加本地环境覆盖 |
| **风险点** | 低（PowerShell 只读检查） |
| **预期收益** | 本地开发检查更完整 |

### 方案 C：激活 shared-for-ai 工作区

| 项目 | 内容 |
|------|------|
| **涉及文件** | `shared-for-ai/` 下的 3 个空目录 |
| **改动内容** | 每个目录新增一个 `.gitkeep` 或简单的 README 说明 |
| **为什么值得做** | 为 AI 工作区建立初始结构 |
| **风险点** | 极低（仅新建空文件） |
| **预期收益** | 明确各子目录用途 |

## 三、自选方案

**选择：方案 A + 方案 B（同时增强服务器和本地检查脚本）**

**理由**：
1. 两个脚本功能互补，增强后形成完整的开发环境检查体系
2. 改动文件数 = 2 个（在 2～5 范围内）
3. 风险极低，均为只读检查
4. 收益明显，提升巡检能力
