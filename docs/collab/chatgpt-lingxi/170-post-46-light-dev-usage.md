# 《基于〈开发环境 4.6版〉的后续轻量开发使用说明》

## 0. 文档用途

本说明不是新一轮“搭环境”文档，也不是一次性的“交给 Codex 执行单”，而是 **《开发环境 4.6版》进入实际使用态之后** 的留存版使用说明。

当前环境已经完成从“规划态”到“可复验落地态”的切换：
本地 Surface + GitHub + Codex CLI 的轻量协作链路已跑通；阶段 7.1~7.5 与阶段 8 已完成；《开发环境 4.6版》与后续轻量开发使用说明都已经落盘；默认轻量任务可直接走本地 Codex + 本地验收；云上腾讯云 / OpenClaw（灵犀）继续保留为更重任务、更长链路和 Agent 常驻执行位。

因此，后续重点不再是继续扩环境，而是 **按当前稳定规则持续使用这套环境做真实小任务**。

---

## 1. 当前统一使用口径

### 1.1 一句话口径

**本地 Codex 负责快、小、清晰的任务；云上灵犀负责长、重、自动化的任务；GitHub 仍是唯一事实版本库；人工主要负责定目标、看结果、做最终验收。**

### 1.2 当前默认策略

1. **本地优先处理轻量任务**  
   例如：文档落盘、小范围脚本提示语修补、help 文案修订、状态总结、session log 更新。

2. **云上优先处理长链路任务**  
   例如：长时间巡检、批量脚本运行、容器试验、日志采集、较重的自动化任务。

3. **GitHub 作为唯一版本基线**  
   不管任务在本地还是云上完成，最终都应以 GitHub 分支结果为准。

4. **当前权限策略可适度放宽，但仍建议保留最小验收动作**  
   尤其是云上环境、测试仓、临时分支内的执行权限，可以比前期试点阶段更宽一些；但每轮仍建议保留 diff 检查与固定验收脚本，避免“做完但不可复验”。

---

## 2. 当前推荐的角色分工

### 2.1 本地 Surface + Codex

适合承担：

- 快速文档生成与修改
- 小范围脚本文案修补
- help / 提示语 / 注释优化
- session log / closeout / playbook 落盘
- 本地 diff 检查
- 本地最小验收
- 提交与推送

当前判断：

**本地 Codex 已经不是试点态，而是可日常使用的轻量执行位。**

### 2.2 云上腾讯云 + 灵犀（OpenClaw）

适合承担：

- 长时间运行任务
- 批处理任务
- 多步巡检
- 自动化报告生成
- 临时依赖安装与试验
- 容器 / 脚本 dry run
- 本地不想长期占用的重任务

当前判断：

**云上灵犀仍然很有价值，重点不是替代本地 Codex，而是承担“更长、更重、更自动化”的执行位。**

### 2.3 人工

当前最适合保留在人手里的动作：

- 选任务目标
- 给出边界与授权
- 看 Codex / 灵犀 回报的 diff
- 跑关键验收命令或确认验收结果
- 决定是否 commit / push / 收口

当前判断：

**人工的核心职责已经从“亲自改文件”转为“控方向、控边界、控验收”。**

## 3. 当前最推荐的三种工作流

## 3.1 工作流 A：本地直做

适用场景：

- 只改 1~3 个文件
- 主要是文档、小修补、提示语调整
- 希望当天快速完成

默认流程：

1. 由你或 ChatGPT 明确任务边界
2. 直接把任务发给本地 Codex
3. Codex 完成后先回报 diff
4. 本地执行固定验收
5. 验收通过后直接 commit / push

这是后续最常用、最高频、最省事的方式。

## 3.2 工作流 B：云上执行

适用场景：

- 任务链较长
- 要跑较多命令
- 要占用更久时间
- 更适合放在云上持续执行

默认流程：

1. 由你或 ChatGPT 给灵犀下发任务
2. 灵犀在云上独立执行
3. 灵犀输出报告、日志、diff 或产物路径
4. 必要时由本地再做一次关键复核
5. 结果写回 GitHub

这是后续最适合利用腾讯云资源与 Agent 自主能力的方式。

## 3.3 工作流 C：本地与云上协同

适用场景：

- 先在云上做巡检 / 批处理 / 试验
- 再在本地做收口、文档、轻量修补

默认流程：

1. 灵犀先在云上跑重任务
2. 输出中间结果、日志、建议修改点
3. 本地 Codex 根据结果做最终小修补或文档收口
4. 本地完成验收、commit、push

这是后续最推荐的常态协作方式。

## 4. 后续可直接放开的任务白名单

当前建议直接放开的任务包括：

### 4.1 文档类

- 方案文档
- playbook
- closeout
- handoff
- session log
- 使用说明
- 状态总结

### 4.2 巡检类

- 仓库扫描
- Markdown 批量巡检
- 路径 / 链接 / 标题格式整理
- 文档索引更新
- 报告导出

### 4.3 低风险脚本类

- help 文案
- 提示语
- 输出文字
- 注释
- 包装层脚本
- 不改核心逻辑的小修补

### 4.4 云上自动化类

- 拉仓 / 更新分支
- 跑脚本
- 生成中间报告
- 日志采集
- 临时依赖安装
- 容器 dry run
- 批处理任务

当前口径：

**以上任务可以优先交给 Codex 或灵犀执行，不必再按前期试点那样过度保守。**

---

## 5. 仍建议保留人工卡口的事项

以下事项，当前仍建议先人工看一眼再放行：

1. 改 `main`
2. 改大量核心逻辑
3. 改依赖版本
4. 改系统级配置
5. 会大范围删文件
6. 会重建云上环境
7. 会引入新的长期常驻服务

这不是因为当前环境不能做，而是因为这些动作已经不属于“后续轻量开发使用说明”的常态范围。

## 6. 后续最推荐的真实用法

后续不要再把重点放在“继续造环境文档”，而是直接开始做这三类小任务：

### 类型 A：文档与规则沉淀

例如：

- 更新某个流程说明
- 生成某个任务模板
- 补充某个 handoff 入口
- 收口某个阶段总结

### 类型 B：仓库轻维护

例如：

- 巡检 docs/
- 修复 help 文案
- 整理报告脚本输出
- 统一提示语和命名

### 类型 C：轻量云上自动化

例如：

- 让灵犀在云上做 repo 巡检并回传报告
- 让灵犀批量生成 markdown 索引
- 让灵犀执行长一点的检查链
- 让灵犀跑容器或脚本试验，再由本地 Codex 收口

## 7. 文档维护口径

这份文档现在已经不是“一次性任务说明”，而是**当前稳定协作方式的留存说明**。

因此，后续维护建议改为以下口径：

### 7.1 何时需要更新本说明

只在以下情况出现时再更新：

1. 默认工作流发生变化
2. 常用验收命令发生变化
3. 本地 / 云上角色分工发生变化
4. 白名单范围明显扩大或收紧
5. Git 分支或协作主路线切换

### 7.2 何时不需要更新

以下情况通常不需要动这份说明：

1. 只是完成了一个普通小任务
2. 只是补了一份 session log
3. 只是修了某个 help 文案
4. 只是增加了一份与本说明平级的专项文档

### 7.3 后续如果要改，建议怎么改

建议仍优先使用本地 Codex 修改，但定位应是：

- **更新现状说明**
- **补充新规则**
- **修正文档与现实不一致处**

而不是再把它写成一次性的“交给 Codex 执行单”。
